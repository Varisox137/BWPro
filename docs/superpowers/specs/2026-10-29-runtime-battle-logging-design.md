# 对战运行日志设计

## 目标

运行日志用于定位本地热坐、CLI 与联机对局问题，完整记录玩家指令、引擎事件和实际执行的原子 op；同时移除 PIL 调试噪声与 GUI 时间线的重复落盘。

## 文件与级别

- 默认目录保持项目根目录 `logs/`。
- 文件名改为 `bwpro-YYYYMMDD-HHMMSS-PID.log`，与 BWPDIY 的单次运行命名风格一致；同一次进程运行只对应一个文件。
- 文件继续记录 DEBUG 及以上，PIL logger 调整为 WARNING 及以上。
- 旧日志仍按现有数量与期限清理策略处理。

## 对战记录埋点

统一在引擎产生结构化 trace（`cmd` / `event` / `op`），本地写运行日志，联机由服务端拥有并下发，避免客户端重复实现：

- `Game.apply(cmd)`：在指令校验前记录当前行动方、阶段与完整 cmd，因此非法输入也可追踪。
- `Game.emit(name, **payload)`：记录事件序号、事件名与完整 payload；事件即使因终局状态不再收集能力，也保留发点记录。
- `Game._run_step(step, ctx)`：仅在 step 条件通过、动态数值与目标解析完成后、调用 op 前记录。内容包括 op 名、实际参数、目标、控制者、来源、相关卡牌与事件上下文；条件不满足而跳过的 step 不算实际原子事件，不记录。
- 本地热坐与 CLI 通过本地 trace sink 写入运行日志。
- 联机客户端只上传主动操作 cmd，不在本地重建事件或 op。服务端通过同一引擎埋点保存完整 trace，并按各观看方的信息权限过滤后增量下发；客户端只把收到的 trace 写入运行日志。非公开手牌、牌库与结算选择信息不得因新通道泄露。

trace 不改变对局状态、事件顺序或既有对局显示协议。

## GUI 对局记录

局内“对局记录”继续展示现有 `state.timeline`，不改为展示 DEBUG 日志。删除 `HotseatView.play_next_timeline` 中把 timeline 文本再次写入运行日志的逻辑，避免与指令、事件和 op 记录重复。

## 测试

- 校验新文件名、项目日志目录与 PIL 过滤。
- 覆盖玩家合法/非法指令、emit payload 和实际 op 参数/目标。
- 覆盖条件不满足的 step 不记录。
- 覆盖本地与联机 GUI 不再重复写入 timeline 文本；联机仅记录服务端下发的过滤后 trace，并校验私有信息不泄露。
- 运行日志相关测试及既有全量测试。
