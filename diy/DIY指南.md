# 把创意交给大模型：DIY 式神与卡牌指南

你不需要会编程，也不需要手写 YAML。准备好一位式神和它的 8 张卡牌创意，把**本文件、你的想法和项目仓库**一起交给能够读写项目文件的大模型，让它协助检查、生成和测试即可。

当前 DIY 采用“YAML 数据 + 游戏已有规则组件”的方式，不是自由编写程序。大模型可以帮你组织数据和效果，但不能保证任何想象出来的规则都已经受支持。

## 一、你需要准备什么

### 1. 式神创意

尽量提供：

- 式神名称。
- 派系：红莲、紫岩、青岚、苍叶，或无相。
- 基础力量与基础生命。
- 基础能力的完整中文描述。
- 能力何时触发、影响谁、持续多久；如果不确定，可以请大模型先帮你分析。

### 2. 八张卡牌创意

每张卡尽量写清：

- 卡名。
- 等级：1、2 或 3。
- 类型：法术、战斗、形态或幻境。
- 稀有度：R、SR 或 SSR。
- 鬼火消耗；不写时通常为 1。
- 完整效果文本。
- 是否需要选择目标，以及可以选择谁。
- 形态牌的力量、生命和持续能力；幻境牌的耐久与队列能力。
- 如果是觉醒牌，说明觉醒后的身材加成与替换能力。

不必担心术语是否标准。先按自然语言描述，再让大模型指出歧义。

### 3. 一个参考格式

```text
式神：名称、派系、力量/生命
基础能力：……

卡牌1：卡名，1级法术，R
效果：……

卡牌2：卡名，2级战斗，SR
效果：……

……
卡牌8：卡名，3级形态，SSR
力量/生命：……
持续能力：……
```

## 二、可以直接交给大模型的话

将下面这段与你的创意一起发送：

```text
请在当前 BWPro 仓库中协助制作一位 DIY 式神及其 8 张卡牌。

请先阅读 diy/DIY指南.md、diy/README.md 和项目 AGENTS.md，
再检查 core/engine.py 等核心结算实现，以及核心动作、事件、目标与现有相似卡牌。

我的创意如下：
【在这里粘贴式神与八张卡牌描述】

请先逐项把效果映射到现有机制，并指出所有歧义或暂不支持的部分。
不要编造 op、事件、条件键或目标键；不要为了单张卡编写不可复用的特殊分支。
如果效果无法由现有机制表达，请明确列出缺少的通用能力，不要写入静默失效的数据。
确认设计后再生成 YAML、补充必要测试并运行校验。
请用非技术语言向我汇报：哪些内容已完成、哪些不能实现、我需要在界面中如何试用。
```

## 三、大模型应遵循的项目规则

以下内容是给执行制作的大模型看的。

### 1. 先检查能力，再写数据

- 主动阅读 `core/engine.py`、`core/model.py`、`core/events.py` 等核心实现，确认事件结算顺序、对象生命周期和状态字段，不能只根据卡面文本猜测行为。
- 卡牌效果只能组合 `core/actions.py` 中已注册的原子 op。
- 事件来自 `core/events.py` 或 `db/events.yaml`。
- 目标使用 `core.targets` 的目标池与 `TargetSpec`。
- 条件键、目标扩展键和动态数值键必须已在 `core/registry.py` 登记。
- 机制未实现时不得写入 YAML；空效果、错误 op 或自造标签不是合法的“临时实现”。
- 如果确需新机制，应优先实现可复用的原子 op 或通用事件，并补充机制测试和文档。

### 2. 使用项目脚手架

不要从零手写整份 YAML。使用 `db.scaffold` 生成式神及 01–08 八张卡的骨架，再逐个补全效果：

```bash
PYTHONIOENCODING=utf-8 ./.venv/Scripts/python.exe -m db.scaffold -h
```

新式神需要唯一 id、拼音 slug 和已登记的版本包目录。目录结构、id 号段与版本包登记分别见 `db/packs.py` 和脚手架说明。不要覆盖已有文件，也不要复用现有式神或卡牌 id。

### 3. 保持版本数据结构

式神与卡牌 YAML 顶层使用：

- `id`
- `name`
- `versions.history` 中的完整版本快照
- 可选的 `versions.best`

卡牌的所属式神由 id 推导，不手写 `shikigami`；鬼火消耗缺省为 1。卡牌主类型使用 `spell`、`combat`、`form`、`field` 等现有值；觉醒使用现有觉醒字段与子类型约定，不自造主类型。

效果块通过 `EffectBlock` 的 `when`、`condition`、`steps`、`mode`、`timing` 等字段表达。每个步骤调用一个已有 op，并按需要配置 `target`、`amount`、`count` 等参数。

可参考 `db/01_jingdian/01_bailang/` 中的简单式神与卡牌，但应优先寻找与目标效果真正相似的现有实现。

### 4. 不修改官方事实来源

`card_data_raw.md` 只用于原版卡牌，任何 agent 不得为了 DIY 修改它。DIY 条目可能产生“raw 无对应条目”的非阻塞警告，这是当前已知行为。

不要为了让校验或显示通过而篡改官方文本、删除其他内容或绕过白名单。

### 5. 美术与规则数据分离

规则 YAML 与卡图配置是两件事：

- 规则数据位于 `db/`。
- 卡图、式神立绘与机制框配置位于 `library/`，由 BWPDIY 渲染体系使用。
- 没有美术配置时仍可使用名称占位卡图进行规则测试。
- 不要因为缺少图片而跳过规则校验，也不要把图片路径写进引擎效果。

### 6. 完成后必须验证

运行数据库校验：

```bash
PYTHONIOENCODING=utf-8 ./.venv/Scripts/python.exe -m db.validate
```

为新增机制和实际卡牌行为补充测试。测试应按机制主题组织，不按式神名单独堆叠文件。至少验证：

- 式神和八张卡都能加载。
- 构筑中能选择该式神，卡牌数量与等级正确。
- 每张卡的消耗、目标与主要效果符合描述。
- 涉及新机制时，覆盖触发时机、目标合法性、持续时间和离场/气绝等边界。
- 热坐中能实际使用；需要联机支持时，再检查服务端下发和客户端显示。

## 四、试用与修改

完成并通过校验后，可启动图形客户端：

```bash
uv run python -m client.gui
```

在卡组构筑中选择该式神并组卡，再进入本地热坐试用。发现效果不符合预期时，把“实际表现”和“你期望的表现”一起交给大模型，比只说“这张卡坏了”更容易修复。

当前 DIY 内容会直接加入项目数据库，没有独立的启用/禁用开关。建议在独立分支或备份中制作，避免与正式内容混在一起。
