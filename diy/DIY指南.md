# 把创意交给大模型：DIY 式神与卡牌指南

你不需要会编程，也不需要手写 YAML。只需把**本文件和一位式神及其 8 张卡牌的原始创意**交给大模型；大模型会按本指南定位并阅读项目核心实现，协助你完善设计、生成 YAML 和测试。

当前 DIY 采用“YAML 数据 + 游戏已有规则组件”的方式，不是自由编写程序。大模型可以帮你组织数据和效果，但不能保证任何想象出来的规则都已经受支持。

## 一、你需要准备什么

### 1. 式神创意

尽量提供：

- 式神名称。
- 派系：红莲、紫岩、青岚、苍叶，或无相。
- 基础力量与基础生命。
- 基础能力的完整中文描述。
- 能力何时触发、影响谁、持续多久；如果不确定，可以请大模型先帮你分析。

### 2. 八张卡牌创意

每张卡尽量写清：

- 卡名。
- 等级：1、2 或 3。
- 类型：法术、战斗、形态或幻境。
- 稀有度：R、SR 或 SSR。
- 鬼火消耗；不写时通常为 1。
- 完整效果文本。
- 是否需要选择目标，以及可以选择谁。
- 形态牌的力量、生命和持续能力；幻境牌的耐久与队列能力。
- 如果是觉醒牌，说明觉醒后的身材加成与替换能力。

不必担心术语是否标准。先按自然语言描述，再让大模型指出歧义。

### 3. 一个参考格式

```text
式神：名称、派系、力量/生命
基础能力：……

卡牌1：卡名，1级法术，R
效果：……

卡牌2：卡名，2级战斗，SR
效果：……

……
卡牌8：卡名，3级形态，SSR
力量/生命：……
持续能力：……
```

## 二、可以直接交给大模型的话

将本指南作为附件，再在对话框发送下面这段。原始创意可通过后续文字、图片或其他附件单独提供，无需复制进指南：

```text
你是 BWPro 的 DIY 制作助手。请阅读随附的 DIY指南.md，
并使用可用工具主动定位、阅读 BWPro 的核心实现，不要假设我已经提供仓库路径。
若本地项目不可用，请从公开仓库 https://github.com/Varisox137/BWPro
在线阅读指南列出的核心源码与相似卡牌数据；不得因未读取实现而编造规则组件。
我的原始创意会通过对话文字、图片或其他附件单独提供，不需要写入指南；
如果尚未收到创意，请先让我提供，不要自行虚构。

不要把原始创意一次性直接转换成 YAML。请先复述你对各项效果的理解，
逐项映射到现有机制，并指出歧义、冲突或暂不支持的部分。

不要编造 op、事件、条件键或目标键；不要为了单张卡编写不可复用的特殊分支。
如果效果无法由现有机制表达，请明确列出缺少的通用能力，不要写入静默失效的数据。
请用非技术语言向我汇报：哪些内容已完成、哪些不能实现、我需要在界面中如何试用。
```

## 三、大模型应遵循的项目规则

以下内容是给执行制作的大模型看的。

### 1. 先理解意图，通过多轮交互完善设计

- 公开项目地址为 https://github.com/Varisox137/BWPro 。本地项目不可用时，使用联网工具读取 GitHub 文件；原始文件可按 `https://raw.githubusercontent.com/Varisox137/BWPro/master/<路径>` 获取。不要依赖训练记忆或凭空猜测项目结构。
- 先阅读核心实现，再判断用户创意如何落地。至少检查 `core/engine.py` 的指令入口、事件发出与队列结算，`core/model.py` 的对象与状态，`core/events.py` 的时机类别，`core/actions.py`、`core/targets.py`、`core/registry.py` 的可用原语和白名单，以及 `db/schema.py`、`db/loader.py`、`db/packs.py` 的数据契约。
- 按创意寻找并在线阅读最相似的现有式神/卡牌 YAML，核对真实字段写法、op 参数和触发时机；不能只读指南中的结构概述就开始生成。
- 如果网络或工具无法取得上述核心实现，应明确说明阻塞并继续与用户确认需求，但不要交付标为“可入库”的 YAML。不得用留空 `effects`/`steps` 的半成品冒充已完成产物。
- 用自己的话复述式神能力和每张卡牌，分别列明触发时机、控制者、来源、目标、数值、费用、持续时间和效果顺序。不要仅凭关键词名称或相似卡面猜测语义。
- 主动识别描述中的歧义，例如“回合”属于哪一方、“角色”是否包含牌手、“所有”是否包含气绝或未升级式神、效果能否叠加、离场或气绝后是否保留。
- 每轮优先询问最影响实现的一个问题；适合时给出少量明确选项。等待用户回答，再根据回答更新理解，不要替用户擅自决定。
- 发现用户描述内部矛盾、与现有机制冲突或多种规则解释均可成立时，说明冲突及后果，与用户共同确定口径。不要静默选择一种解释后直接写数据。
- 设计确认前输出逐项“自然语言效果 → 现有 op/事件/目标”的映射；无法映射的条目单独列出。确认后再创建文件，并在实现后复查是否偏离确认过的意图。

### 2. 先检查能力，再写数据

- 卡牌效果只能组合 `core/actions.py` 中已注册的原子 op。
- 事件来自 `core/events.py` 或 `db/events.yaml`。
- 目标使用 `core.targets` 的目标池与 `TargetSpec`。
- 条件键、目标扩展键和动态数值键必须已在 `core/registry.py` 登记。
- 机制未实现时不得写入 YAML；空效果、错误 op 或自造标签不是合法的“临时实现”。
- 如果确需新机制，应优先实现可复用的原子 op 或通用事件，并补充机制测试和文档。

### 3. 使用项目脚手架

不要从零手写整份 YAML。使用 `db.scaffold` 生成式神及 01–08 八张卡的骨架，再逐个补全效果：

```bash
PYTHONIOENCODING=utf-8 ./.venv/Scripts/python.exe -m db.scaffold -h
```

新式神需要唯一 id、拼音 slug 和已登记的版本包目录。目录结构、id 号段与版本包登记分别见 `db/packs.py` 和脚手架说明。不要覆盖已有文件，也不要复用现有式神或卡牌 id。

### 4. 保持版本数据结构

式神与卡牌 YAML 顶层使用：

- `id`
- `name`
- `versions.history` 中的完整版本快照
- 可选的 `versions.best`

卡牌的所属式神由 id 推导，不手写 `shikigami`；鬼火消耗缺省为 1。卡牌主类型使用 `spell`、`combat`、`form`、`field` 等现有值；觉醒使用现有觉醒字段与子类型约定，不自造主类型。

效果块通过 `EffectBlock` 的 `when`、`condition`、`steps`、`mode`、`timing` 等字段表达。每个步骤调用一个已有 op，并按需要配置 `target`、`amount`、`count` 等参数。

可参考 `db/01_jingdian/01_bailang/` 中的简单式神与卡牌，但应优先寻找与目标效果真正相似的现有实现。

### 5. 不修改官方事实来源

`card_data_raw.md` 只用于原版卡牌，任何 agent 不得为了 DIY 修改它。DIY 条目可能产生“raw 无对应条目”的非阻塞警告，这是当前已知行为。

不要为了让校验或显示通过而篡改官方文本、删除其他内容或绕过白名单。

### 6. 美术与规则数据分离

规则 YAML 与卡图配置是两件事：

- 规则数据位于 `db/`。
- 卡图、式神立绘与机制框配置位于 `library/`，由 BWPDIY 渲染体系使用。
- 没有美术配置时仍可使用名称占位卡图进行规则测试。
- 不要因为缺少图片而跳过规则校验，也不要把图片路径写进引擎效果。

### 7. 完成后必须验证

运行数据库校验：

```bash
PYTHONIOENCODING=utf-8 ./.venv/Scripts/python.exe -m db.validate
```

为新增机制和实际卡牌行为补充测试。测试应按机制主题组织，不按式神名单独堆叠文件。至少验证：

- 式神和八张卡都能加载。
- 构筑中能选择该式神，卡牌数量与等级正确。
- 每张卡的消耗、目标与主要效果符合描述。
- 涉及新机制时，覆盖触发时机、目标合法性、持续时间和离场/气绝等边界。
- 热坐中能实际使用；需要联机支持时，再检查服务端下发和客户端显示。

## 四、试用与修改

完成并通过校验后，可启动图形客户端：

```bash
uv run python -m client.gui
```

在卡组构筑中选择该式神并组卡，再进入本地热坐试用。发现效果不符合预期时，把“实际表现”和“你期望的表现”一起交给大模型，比只说“这张卡坏了”更容易修复。

当前 DIY 内容会直接加入项目数据库，没有独立的启用/禁用开关。建议在独立分支或备份中制作，避免与正式内容混在一起。
