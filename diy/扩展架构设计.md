# DIY 扩展架构设计

状态：**本地运行时、内置内容包、联机同步与设置页清理已实现**。本文规定本项目如何承载 DIY，不记录具体式神或卡牌设计。

## 1. 目标与边界

- 正式内容继续存放在 `db/`，DIY 内容不合并到正式目录。
- 正式引擎只提供通用扩展点，不出现 DIY 包名、式神名、卡牌名或专属分支。
- 包级共享机制与式神级私有机制分别跟随对应内容目录，不在中央 Python 文件中累积。
- 用户创意以文本、图片和 YAML 表达；不从用户输入动态执行 Python。
- 本地热坐、构筑、GUI 与联机共用同一套规则数据和结算结果。
- 联机服务端不持久化保存用户 DIY 内容，但在房间存续期间必须于内存中持有权威结算所需的数据。

## 2. 自有内容与下载内容

### 自有内容

仓库内置或用户自己制作的内容位于项目的 DIY 工作区：

```text
diy/content/
```

它由用户主动编辑，联机清理不得删除。

### 联机下载内容

从其他玩家取得的包保存到用户目录，不直接写入项目仓库：

```text
~/.bwpro/diy/<包id>/<内容哈希>/
```

其来源标记为 `downloaded`，记录接收时间、包 id 和内容哈希。同一包的多个下载版本按哈希隔离，不互相覆盖。

用户若修改下载内容，应另存为新的自有版本；修改后的数据不再冒充原下载版本。

## 3. 内容包目录与机制拆分

采用“包级共享、式神级私有、自动发现”的结构：

```text
diy/
├── runtime.py                 # 通用发现、注册与加载流程
├── README.md
├── DIY指南.md
├── 扩展架构设计.md
└── content/
    └── 101_<某主题包>/
        ├── pack.yaml           # 包级元数据
        ├── mechanisms.py       # 该包多个式神共享的新机制
        ├── events.yaml         # 包级共享事件
        └── 01_<某式神>/
            ├── mechanisms.py   # 仅该式神使用的新机制
            ├── events.yaml     # 仅该式神使用的事件
            ├── 110101.yaml
            ├── 11010101.yaml
            └── ...             # 其余卡牌
```

单卡专用机制也放在所属式神目录。只有确认被同包多个式神共享时，才上移到包目录。其他包需要同一能力时，应抽取为正式通用能力，而不是形成跨包隐式依赖。

### `mechanisms.py`

该文件注册当前层所需的：

- 原子 op。
- 条件与目标池。
- 动态数值与光环求值器。
- 必须配合引擎的其他行为。

核心只提供注册接口；具体实现跟随内容包。注册名在全局运行时必须唯一，重复注册直接报错。

### `events.yaml`

声明当前层新增的事件名及 `insert`/`queue` 时机。事件应与使用该事件的机制位于同一层。

### `pack.yaml`

包级元数据可包含：

- 包 id、名称、主题与作者。
- 内容哈希。
- 所需 op、事件和机制能力清单。
- 可选的最低客户端版本。

## 4. 制作者信息

式神 YAML 顶层增加可选 `author`，可留空，并随环境解析保留：

```yaml
id: 110101
name: 示例式神
author: "作者标识"
versions:
  history:
    - date: 20261113
      # 完整规则数据
```

`author` 是元数据，不参与结算。脚手架与版本校验允许该字段，但它不进入规则快照。

## 5. id 与版本约定

沿用统一 id 规则：

- 式神：`avvvss`。
- 专属卡牌：`avvvsscc`。
- 中立牌：`a999xxxx`，版本包 999 保留给中立牌。
- 首位 `a` 为异画位，默认 1；后三位为版本包号。
- DIY 包默认从 101 起递增；这不是硬性限制，只需避开官方包号与中立包 999。

DIY 与正式数据共享 id 唯一性约束。发生以下情况时拒绝加载或开局，并报告冲突 id 与来源：

- 不同包存在相同式神或卡牌 id。
- 同一运行环境中出现重复 id。
- 卡牌 id 前缀与所属式神不一致。

不做自动 id 重映射，因为卡组码、归属、效果引用和美术配置都依赖稳定 id。

## 6. 自动发现与加载

`diy/runtime.py` 不维护包名或式神名清单，执行固定流程：

1. 按“包目录先于子目录、同层按路径排序”发现 `mechanisms.py` 与 `events.yaml`。
2. 注册其中的 op、事件、条件、目标与光环求值器。
3. 分别加载正式 `db/`、项目 DIY 工作区及允许使用的下载内容。
4. 对合并结果执行 id 查重、schema、事件、op、目标与白名单校验。
5. 构造运行时 `CardDatabase`，供构筑、热坐和联机使用。

新增或删除 DIY 包只需增删对应目录，不修改中央 Python 清单。加载失败必须明确报错，不能静默禁用内容或留下空效果。

正式文本仍以 `card_data_raw.md` 为唯一事实来源；DIY 文本不写入该文件，正式 raw 对齐校验与 DIY 校验分开处理。

## 7. 日期与平衡性环境

DIY 沿用 `versions.history` 完整快照和现有环境解析规则：

- `history.date` 决定该快照从哪个环境日期开始可用。
- 不显式填写、默认使用创建日期时，只能叠加到标准最新环境。
- 若用于过去的平衡性环境，必须显式提供不晚于目标环境的日期。
- 多个修订仍按目标环境选择不晚于该日期的最新快照。
- 日期须合法且严格递增；日期本身不是内容版本身份，内容一致性另由哈希保证。

同步后若卡组包含房间环境下不可用的内容，卡组校验失败，不得开局。

## 8. 联机入口

联机界面增加独立选项：

```text
[ ] 启用 DIY 内容
```

默认不勾选。未勾选时保持现有创建、加入、构筑与开局流程。勾选后创建独立 DIY 房间，不影响普通房间或正式数据库。

## 9. 联机同步协议

同步发生在双方确认卡组并准备之后、开始倒计时之前：

```text
双方确认卡组并准备
  → 房间进入 DIY_SYNCING
  → 双方上报本地包清单（包 id + 内容哈希）
  → 服务器计算双方缺少的包
  → 持有方上传其拥有而对方缺少的完整包
  → 服务器校验并暂存于房间内存
  → 缺少方下载、校验并加载
  → 双方回传同步完成
  → 服务端重新校验双方卡组与房间环境
  → 进入原有开始倒计时
```

协议消息：服务端以 `diy_sync_request` 请求清单，以 `diy_upload_request` 请求完整包，以 `diy_package` 下发包，以 `diy_sync_state` 下发本局完整清单；客户端分别应答 `diy_manifest`、`diy_pack`、`diy_sync_done`，处理失败上报 `diy_sync_error`，服务端以 `diy_sync_failed` 通知双方。包体为 `pack_id`、`content_hash` 和相对路径到 YAML 文本的 `files` 映射。相同清单、上传与完成消息幂等，重复下载直接复用已校验目录。

同步失败时返回大厅并显示原因，不进入对局。重连继续使用原房间的内存快照；房间解散后释放，不写磁盘、不进入全局数据库。

### 同步粒度

按完整 DIY 包同步，不按单卡拆分，以避免包级机制、事件或式神依赖缺失。

### 内容哈希

哈希覆盖解析后规范化的完整 YAML 与包元数据，而不是文件原始文本，避免缩进、换行和键顺序造成假冲突。计算时排除 `pack.yaml` 的 `content_hash` 字段本身，避免循环定义。上传方、服务器与下载方均重新计算并核对。

### 冲突处理

- 同包 id、同哈希：复用同一内容。
- 同包 id、不同哈希：视为版本冲突，必须由双方使用同一版本，否则不能开局。
- 不同包的式神或卡牌 id 冲突：拒绝该组合。
- 不允许用较新日期、较高版本号或上传先后顺序静默覆盖冲突内容。

### 机制代码限制

同步只传输 YAML 与元数据，不传输或执行 `mechanisms.py`。

服务端只能使用启动时已注册的可信 op 和事件。若下载包声明的机制在服务端或接收方当前版本中不存在，即使 YAML 同步成功也拒绝开局，并提示更新或移除该包。不能以同名 op 在不同端的未知实现继续结算。

## 10. 服务端存储与日志

- 服务端只在房间内存中保存当前 DIY 快照。
- 不写入持久数据库，不作为公共内容库保存。
- 日志最多记录包 id、内容哈希和错误摘要，不记录完整 YAML。
- 房间回收时同步释放上传缓存与房间数据库。

## 11. 设置页与清理

设置页增加：

```text
清除联机下载的 DIY 内容
```

不使用“清除所有 DIY 数据”作为按钮名称，因为实际只清理下载内容。

点击后：

1. 显示将删除的下载包数量与占用空间，并要求确认。
2. 只删除 `~/.bwpro/diy/` 中标记为 `downloaded` 的内容。
3. 保留用户自己制作的 YAML、图片与编辑记录。
4. 当前房间仍在使用相关下载内容时禁止清理，提示先离开该 DIY 房间。

## 12. 安全与验证

- 用户输入不经过 `eval`，不动态执行上传代码。
- 所有 YAML 均执行 schema、id、日期、op、事件、条件和目标校验。
- 每方清单至多 32 包；每包至多 128 个 YAML 文件、单文件 256 KiB、总文本 512 KiB，防止异常内容耗尽资源。
- 正式引擎测试与 DIY 行为测试均放在项目 `tests/`，按机制主题组织。
- 至少覆盖自动发现、包级/式神级注册、重复注册、id 冲突、日期环境、同步哈希、断线重连、房间释放与下载内容清理。

## 13. 明确不做的事项

首版架构不包含：

- 从网络或客户端动态加载 Python 机制代码。
- 服务端永久保存或公开分发用户 DIY 内容。
- 自动修复 id、日期或内容哈希冲突。
- 将 DIY 条目写入正式 `db/` 或 `card_data_raw.md`。
- 用空 `effects`/`steps` 冒充已完成且可入库的内容。
